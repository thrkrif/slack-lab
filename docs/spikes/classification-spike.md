# M31 분류 스파이크 (4단계, 2026-10-07)

목적: 4단계 설계가 기대는 두 사실을 코드 없이 먼저 확인한다 — (1) qwen2.5 3b·7b가 라벨 한 단어를 안정적으로 내는가 (2) 분류 모델 + 답변 7b + bge-m3를 한 노트북에 동시에 올릴 수 있는가. 판정 근거가 아니라 설계 입력이다(표본 20개·1회).

환경: MacBook(RAM 16GB), Ollama 0.34.0 호스트, 컨텍스트 4096, 모델 `qwen2.5:3b`(2.2GB 적재)·`qwen2.5:7b`(4.7GB)·`bge-m3`(673MB). **측정 중 스왑이 21.0/21.5GB로 거의 찬 상태였다**(IntelliJ·VM 등 다른 프로세스 상주) — 동시 적재 결과는 이 부하 조건의 결과이며 여유 있는 장비에서는 달라질 수 있다. 스크립트 `docs/spikes/classification_spike.py`(temperature 0, max_tokens 16, 질문은 데이터 블록으로 감쌈), 질문 20개(장애 8·단순 6·정보 부족 6)는 이 스파이크 전용이고 M32 평가 세트와 겹치지 않게 재사용하지 않는다.

## 1. 라벨 신뢰도
| 모델 | 정확 | 무효 출력 | 장애 재현율 | 지연 p50 | 첫 호출(콜드) |
|---|---|---|---|---|---|
| qwen2.5:3b | 15/20 | 0 | 8/8 | 0.30s | 4.0s |
| qwen2.5:7b | 15/20 | 0 | 8/8 | 0.61s | 7.3s |
- 멈춤선(14/20 미만 또는 장애 재현율 7/8 미만)에 **해당 없음** — 둘 다 통과.
- 오답은 거의 **정보 부족 → 장애**(3b 3건 + 단순→정보 부족 1건 + 정보 부족→단순 1건, 7b 5건 모두 정보 부족→장애). 즉 되묻기를 덜 하는 쪽으로 틀린다 — fail-open 방향과 같아 안전하다. 단순 질문을 정보 부족으로 오판한 건은 3b의 `git rebase vs merge` 1건(봇이 답을 거부하는 방향, C2 NEEDS_INFO 오판 상한이 겨냥하는 사례).
- 정보 부족이 약점이다. 한 줄짜리 모호한 질문("서버가 이상해요")을 둘 다 장애로 본다 → M32에서 라벨 정의를 명확히 하고 프롬프트에 예시를 넣는 것이 과제.

## 2. 동시 적재 (핵심 발견)
순서를 바꿔 `ollama ps`로 확인했다.
| 올린 순서 | 결과 |
|---|---|
| 7b → bge-m3 | **공존**(7b 4.7GB + bge-m3 673MB) |
| (7b·bge-m3 상주) → 3b 호출 | 7b가 **축출**되고 3b + bge-m3만 남음 |
| (3b·bge-m3 상주) → 7b 호출 | 3b와 bge-m3가 **축출**되고 7b만 남음, 7b 재적재 **8.6s** |
- 이 장비·부하에서 **3b와 7b는 동시에 상주하지 못한다.** 분류(3b)와 답변(7b)을 번갈아 부르면 요청마다 모델 재적재(최대 약 8.6s)가 일어난다. 전체 스택 20건 순차 답변 p95 6.4s(§21)와 50초 예산을 고려하면 치명적이진 않지만 지연을 더한다.
- 같은 모델을 쓰는 구성(분류=답변)은 재적재가 없다. 이 경우 분류 지연은 웜 0.3~0.6s, 콜드 4~7s.

## 3. 판단 (PLAN 4단계 M31 규칙 적용)
- 계획의 규칙: "동시 적재 불가면 '분류 모델 = `llm.model`' 구성으로 계속(사용자에게 알림)". → 적용한다. 단 이 경우 **3b 분류 + 7b 답변이라는 P2-6의 원래 의도(경량 분류로 지연·메모리 절감)가 이 장비에서는 성립하지 않는다**는 점을 사용자에게 알리고 결정을 받는다(PLAN 핸드오프에 기록).
- 정확도는 3b와 7b가 같으므로(표본 한계) 분류 모델 선택은 지연·메모리가 정한다.
- 역할 분리 설정(`classification.model`) 자체는 유지할 가치가 있다: 메모리가 더 큰 장비에서는 분리가 성립하고, 같은 모델을 쓰는 설정도 합법이다.

정리: 측정 뒤 `ollama stop`으로 세 모델을 모두 내렸다(`ollama ps` 비어 있음).
