## 질문별 답변 초안

### Q1. 3단계 목표 이해가 맞는가 — **PRD/AGENTS.md 기준 "3단계"로는 맞다. 다만 ARCHITECTURE.md 내부 세부 단계로는 두 개(3·5단계)에 걸쳐 있다 — 이 구분이 v2까지 빠져 있었다(Critic MAJOR-1).**

근거: `PRD.md` §3 Flow B(L92-103) "모니터링이 장애 감지 → Slack 알림 → n8n이 수신 API로 전달 → AI가 알림+과거 유사 장애 묶어 초안 리포트 → 스레드에 '추정 원인/과거 유사 사례/1차 대응' 형태로 답", §4 목록(L155-166) P2-4(RAG 전후 비교) · P2-7(Slack 외 입력) · P2-8(알림→리포트 자동화), §6 성공 기준(L230-233) "RAG 전후 답변 품질 차이" · "모니터링 알림 하나로 리포트가 자동 생성된다". PRD §4 원문 표현은 정확히 "**P2 — 3단계 이후**"(L155)이고 AGENTS.md 12행도 같은 3단계 뭉치를 가리킨다 — 사용자가 "3단계"라 부른 범위(=P2 전체) 자체는 이 원문 표현과 맞는다.

**그런데** `ARCHITECTURE.md` §5 진화 표(L365-371)는 "3단계 이후"를 다시 셋으로 쪼갠다: **3단계 = 임베딩·Vector DB(RAG)**, **4단계 = LangGraph·멀티 모델**, **5단계 = n8n·모니터링**. 사용자가 설명한 두 가지 — "장애 기록 + 과거 유사 사례로 원인 안내"(RAG)와 "장애가 발생하면"(알림이 트리거가 되는 자동화, Flow B) — 는 ARCHITECTURE 기준으로 각각 **3단계(RAG)**와 **5단계(n8n·모니터링)**에 해당한다. 즉 하나의 "3단계"가 아니라 두 개의 하위 단계가 합쳐진 그림이다.

PRD §8 표에는 추가하지 않는다(이미 정해진 사실 확인이라 "열린 질문"이 아님). 다만 이 용어 차이는 답변에서 직접 짚어준다 — 나중에 "3단계 작업"이라고 말할 때 RAG만 가리키는 건지, 알림 자동화까지 포함하는 건지 헷갈릴 수 있어서다.

### Q2. "기존 서비스에 부착"이 로컬에서 실제로 가능한가 — **부분적으로 가능. "바로 꽂힘"은 아니고 "이벤트 계약을 맞추면 붙는" 구조.**

근거/분석:
- `PRD.md` §1.2 "AI는 독립된 챗봇이 아니라 기존 서비스 안의 한 컴포넌트다" → "다른 앱 바이너리에 라이브러리로 임베드"가 아니라 "다른 서비스가 만드는 이벤트를 이 서비스가 받아 처리하는 축을 맡는다"는 뜻(Architect 확인: 사이드카/플러그인 해석은 아니다).
- 현재 인바운드 계약은 Slack Events API 페이로드 스키마 하나뿐이다(`SlackEventController`). 다른 로컬 서비스의 알림을 그대로 받을 수는 없고, 그 서비스의 알림 → 이 서비스 입력 스키마로 바꿔주는 변환 계층이 필요하다 — 이게 정확히 PRD §3 L102-103 "입력이 둘 이상이 되는 순간부터 n8n이 값을 한다"가 말하는 지점이다.
- Ollama는 로컬에서 이미 열려 있으니, 다른 로컬 서비스가 이 프로젝트와 별개로 Ollama를 직접 쓰는 것 자체는 지금도 가능하다(공유 인프라라 이 프로젝트 소유가 아님).
- 결론: **"프로세스를 나란히 띄우고 이벤트 계약을 맞춰 HTTP로 밀어넣는" 방식으로는 지금도 가능**하지만, **"내 다른 서비스의 알림 포맷을 그대로 이해해서 바로 붙는다"는 의미로는 아직 안 된다** — 그 변환 계층(n8n 또는 커스텀 어댑터)이 ARCHITECTURE §5 기준 **5단계(P2-7, n8n·모니터링)** 스코프다(Q1에서 정리한 용어로: 3단계가 아니라 5단계).

PRD.md §8 반영안(신규 행): "Slack 외 인바운드를 n8n으로 고정할지, 서비스별 커스텀 어댑터도 허용할지 | 5단계(P2-7, ARCHITECTURE §5) 착수 전"

### Q3. OSS 배포 시 설치 복잡도가 너무 높지 않은가 — **실제 문제 맞음. 지금은 해결하지 않는다(범위 밖), 완화 옵션만 기록해둔다.**

근거/분석:
- `AGENTS.md` "자동으로 넘어가지 않고 멈추는 지점"(Git 규칙): Slack 화면 조작(스코프 재설치·채널 초대·이벤트 구독 활성화)·ngrok URL 재등록이 이미 "사람이 개입해야 하는 지점"으로 명시돼 있다 — 지금 개발자 본인도 매번 겪는 걸 알면서 자동화하지 않기로 한 상태.
- `AGENTS.md` M1 결정(Git 규칙): "1인 학습 프로젝트, 서식 강제·외부 도구 설치 비용이 이득보다 크다" 톤이 이미 있다. `PRD.md` §8 L254 "결정이 필요해지는 시점에 답한다. 미리 정하지 않는다"는 원칙이 이 프로젝트 전반의 태도다.
- **Non-goal 재확인(Critic MAJOR-3, v2의 오독 정정)**: `PRD.md` §7 L241 "멀티 워크스페이스·멀티테넌시 — **워크스페이스 하나만 다룬다**"는 "인스턴스 하나가 여러 워크스페이스/조직을 동시에 서빙하지 않는다"는 뜻이다. **조직마다 각자 내려받아 설치하는 self-hosted OSS는 인스턴스당 워크스페이스가 여전히 하나라 이 non-goal에 걸리지 않는다.** 이 non-goal에 걸리는 건 **하나의 인스턴스가 여러 조직을 서빙하는 호스팅형 멀티테넌트 SaaS**뿐이다 — v2에서는 "OSS 배포 자체가 non-goal과 상충"이라고 잘못 썼다.
- 즉 사용자가 걱정한 "오픈소스로 내놓으면 설치자가 다 해야 하는" 시나리오(=self-hosted, 조직당 인스턴스 1개)는 **애초에 non-goal에 걸리지 않는다.** 문제는 그게 정말로 복잡한가이지, "해도 되는가"가 아니다.
- 지적 자체는 타당하다: Slack App Manifest(YAML/JSON 한 번으로 스코프·이벤트 구독·Request URL 선언)로 앱 생성·스코프 설정은 스크립트화할 수 있지만, ngrok URL은 프로세스를 새로 띄울 때마다 바뀌므로 "설치 1회"가 아니라 "실행할 때마다"의 문제라 매니페스트로 못 없앤다 — 고정 도메인 터널(유료 ngrok, Cloudflare Tunnel named tunnel)이나 자체 도메인+TLS가 있어야 근본적으로 없앨 수 있다. (반면 하나의 인스턴스로 여러 조직을 서빙해 설치 자체를 없애는 "SaaS화"는 non-goal과 정면으로 부딪혀 이 프로젝트 범위에서 제외한다.)
- 결론: self-hosted 설치 복잡도는 실제 문제이고 완화 옵션(App Manifest·고정 도메인)도 존재하지만, 지금은 문서화만 하고 실행하지 않는다 — 이 프로젝트가 "여러 사람이 실제로 설치해 쓰는 배포물"을 목표로 삼기로 결정할 때(현재 §7에 그런 목표 명시 없음, 즉 아직 결정된 바 없음이지 기각된 바 아님) 다시 연다.

PRD.md §8 반영안(신규 행, §7 non-goal 참조로 축약 — 상세 근거는 위 답변 텍스트): "OSS self-hosted 배포 시 설치 자동화 수준(App Manifest / 고정 도메인 터널). SaaS 호스팅은 §7 non-goal이라 제외 | 배포용 오픈소스를 실제 목표로 삼기로 결정하는 시점"

### Q4. 회사 LLM(Codex/Claude)을 `/slack-ai codex`처럼 런타임에 고를 수 있어야 하나 — **아이디어 자체는 타당하지만, 지금 결정하지 않는다. "안 된다"가 아니라 "순서가 있다".**

근거/분석:
- **기존 요구사항과의 관계**: `AGENTS.md` 스택 절 "API 비용 0원이 요구사항"과 `PRD.md` §5 L174 "LLM 추론 비용 0원, 유료 API를 쓰지 않는다"가 **기본값**이다. 다만 이게 절대 금지는 아니다 — `PRD.md` §5 L211-212가 이미 "나중에 Groq·Gemini·유료 API로 바꿀 때 `base-url`만 고치면 된다"고 명시해, 유료 벤더로의 전환 자체는 이미 예상돼 있다(v1에서 "정면 충돌"이라 한 건 과장, Architect 지적 반영).
- **차이점**: 지금 있는 건 **배포 단위의 정적 교체**(`llm.base-url` 하나, 운영자가 설정)다. 사용자가 제안한 건 **요청 1개마다 사용자가 고르는 런타임 라우팅**이라 다른 기능이다.
- **왜 더 어려운가**:
  1. 스키마: OpenAI 호환 스키마 하나로 고정해서 단순함을 얻었다(규칙 3). Claude(Anthropic Messages API)는 OpenAI 스키마가 아니므로 벤더별 변환 로직이 필요하다. `LlmClient` 인터페이스 자체는 다중 구현을 이미 지원하는 구조(`OpenAiCompatibleLlmClient` 외 `EchoLlmClient` 존재)라 확장은 가능하지만, "스키마 하나만 알면 된다"는 단순함은 깨진다.
  2. 인증/비밀 관리: 벤더마다 API 키가 늘고 `.env`·Git 규칙(비밀값 커밋 금지) 관리 대상이 늘어난다.
  3. 비용 추적: 지금은 계측이 없다. 과금 벤더를 붙이면 "누가 얼마나 썼는지" 추적이 새로 필요해진다.
  4. **새 인바운드 경로**(Architect 지적, v1에 없던 내용): `/slack-ai codex` 같은 Slack Slash Command는 그 자체로 새 이벤트 계약이다. Slash Command를 Slack 앱에 등록하려면 Slack 화면 조작이 필요해 `AGENTS.md` 57행 "자동으로 넘어가지 않고 멈추는 지점"에 해당한다 — 코드만으로 끝나는 기능이 아니다.
- **완화 여지**: "전부 허용" vs "전부 금지"가 아니라 중간 지점이 있다. (a) 로컬 Ollama 안의 여러 모델만 허용 목록으로 라우팅(0원 유지, `PRD.md` P2-6 "역할별로 모델을 나눈다"와 자연스럽게 겹친다 — ARCHITECTURE §5 기준으로는 **4단계**(LangGraph·멀티 모델) 스코프다) (b) 클라우드 벤더는 기본 꺼짐 + 명시적 opt-in(설정으로 켜야만 동작, 기본 경로는 여전히 0원).
- **(b)에 대한 추가 제약(Critic MAJOR-4)**: 클라우드 벤더 opt-in은 비용(§5 L174)뿐 아니라 `PRD.md` §5 L178 "**대화 내용이 외부 API로 나가지 않는다**"와도 부딪힌다 — 이건 "로컬 추론의 부수 효과이자 장점"이라고 명시된 요구사항이다. 즉 opt-in을 켜는 순간 비용 요구사항과 데이터 반출 금지 요구사항 **둘 다** 예외가 발생한다는 걸 사용자가 명확히 인지하고 켜야 한다 — "그냥 설정 하나 추가"로 가볍게 볼 사안이 아니다.
- **회사 사용 시나리오 자체는 타당하다** — 다만 이건 이 개인 학습 프로젝트의 현재 로드맵(1~5단계, PRD/ARCHITECTURE §5)에 없는 항목이라, 회사에서 실제로 쓰는 도구로 진화하기로 별도 결정할 때 붙는 기능으로 보는 게 맞다. 로컬 다중 모델(완화안 a)만이라면 4단계 스코프 안에서 자연스럽게 다룰 수 있지만, 클라우드 벤더(완화안 b)는 0원·데이터 반출 요구사항 자체를 재검토해야 해서 별도 결정이 선행돼야 한다.

PRD.md §8 반영안(신규 행, 상세 근거는 위 답변 텍스트): "런타임 LLM 벤더 선택(`/slack-ai codex` 등) 지원 여부 — 로컬 다중 모델(4단계)까지만 할지, 클라우드 opt-in까지 열지 | 회사 도입을 실제로 검토하기로 결정하는 시점, Slash Command 인바운드 설계와 함께"

## ADR

- **Decision**: 4개 질문 중 Q1(사실 확인 — 단, ARCHITECTURE 내부 3/5단계 구분을 짚어줌)은 답변만 전달하고 문서에 추가하지 않는다. Q2·Q3·Q4(실제로 열린 결정)는 `PRD.md` §8 "열린 질문" 표에 행 3개로 기록한다. ARCHITECTURE.md·코드는 지금 바꾸지 않는다.
- **Drivers**: 단계를 앞지르지 않는다(규칙 1), 기존 문서 구조를 존중한다(PRD §8이 이미 이 역할), 0원 비용 요구사항은 유료 벤더 전환을 이미 예상한 기본값이라 예외 여지가 있지만(PRD L211-212) 데이터 반출 금지(L178)는 그런 예외 근거가 문서에 없어 더 엄격하게 다뤄야 한다는 점을 구분해서 반영, 1인 학습 프로젝트 실용주의(M1 결정과 동일 톤), non-goal은 self-hosted 배포가 아니라 SaaS 호스팅에만 해당한다는 정확한 해석(PRD L241).
- **Alternatives considered**: (A) 답변만 채팅, 문서 미반영 — 기각(맥락 유실). (B) 4개 전부 표에 추가 — 기각(Q1은 이미 정해진 사실이라 "열린 질문" 표에 넣으면 오해를 줌). (D) ARCHITECTURE.md §5 진화 표 옆에 주석 — 기각(그 표는 "무엇이 바뀌는지"를 기록하는 곳이지 미결정 질문을 기록하는 관례가 없음). (v1에서 고려했던 "ARCHITECTURE.md 새 절 추가"도 Architect 검토로 기각 — 기존에 이미 PRD §8이라는 정확히 맞는 자리가 있었음.)
- **Why chosen**: PRD §8이 정확히 "결정이 필요해지는 시점에 답한다"는 목적으로 이미 운영 중인 표라, 새 구조를 만들지 않고 그 관례를 그대로 잇는 것이 가장 적은 변경으로 가장 정확하다. Q2·Q4 행에는 관련 ARCHITECTURE §5 단계 번호를 괄호로 명시해 옵션 D의 장점(문맥 연결)도 일부 살렸다.
- **Consequences**: PRD.md에 행 3개 추가(문서 전용 커밋 1건, 브랜치 `feature/docs-open-questions-p2`). 세 미해결 질문은 각자의 결정 시점까지 실행되지 않는다 — 특히 런타임 벤더 선택은 사용자가 명시적으로 다시 꺼내기 전까지, 그리고 0원·데이터 반출 요구사항을 먼저 재검토하기 전까지 누구도 먼저 진행하면 안 된다는 제약을 남긴다.
- **Follow-ups**: (1) 사용자가 이 계획 내용에 승인하면(실행 타임라인의 "내용 승인" 단계) PRD.md 문서 커밋을 진행하고, 이후 브랜치~PR 병합은 AGENTS.md Git 규칙에 따라 추가 승인 없이 자동 진행한다. (2) 5단계(P2-7) 착수 시 인바운드 어댑터 질문 재론. (3) 회사 도입 검토 시 로컬 다중 모델(4단계, P2-6)부터 먼저 볼지, 클라우드 opt-in(0원·데이터 반출 요구사항 재검토 선행)까지 갈지 논의. (4) AGENTS.md 12행의 단계 표기 불일치는 사용자에게 별도로 알리고, 이 계획과 무관하게 처리 여부를 묻는다.
