## 1. 왜 필요한가

### 1.1 해결하려는 문제

팀에 장애가 나면 이런 일이 반복된다.

- 같은 장애가 몇 달 뒤 다시 난다. **누군가는 겪었지만 기록은 스레드 어딘가에 묻혀 있다.**
- 당직자가 과거 사례를 찾는 데 시간을 쓴다. 검색어를 잘 고르는 것부터가 요령이다.
- 정리해 두자고 해도, 장애 대응이 끝난 직후가 문서를 쓰기 가장 어려운 시점이다.

지식은 이미 Slack에 있다. 꺼내 쓰지 못할 뿐이다.

### 1.2 왜 지금, 왜 이 방식인가

Hooks나 Skills로 만든 자동화는 **사람이 터미널에서 명령을 입력해야 돌아간다.**
그건 도구를 쓴 것이지, 시스템을 만든 것이 아니다.

이 프로젝트는 그 반대를 만든다.

- 트리거는 사람이 아니라 **이벤트**다 (Slack 메시지, 나중에는 모니터링 알림)
- AI는 독립된 챗봇이 아니라 **기존 서비스 안의 한 컴포넌트**다
- 그래서 큐·재시도·멱등성·관측 같은, **백엔드가 원래 감당하던 문제들이 그대로 따라온다**

### 1.3 이 프로젝트의 이중 목적

정직하게 적어둔다. 두 가지를 동시에 노린다.

| 목적 | 성공의 모습 |
|---|---|
| **학습** (주) | "AI 붙여봤다"가 아니라 "AI를 시스템 안에서 어떻게 돌아가게 했는가"를 구조로 설명할 수 있다 |
| **도구** (부) | 개인/소규모 팀이 실제로 켜두고 쓸 만한 수준까지 간다 |

학습이 우선이라, **각 부품은 "없어서 불편해진 다음에" 넣는다.**
처음부터 완성형 아키텍처를 세우지 않는 것이 의도다.

## 2. 사용자 타겟

### 2.1 1차 사용자 — 만드는 사람 (나)

- 백엔드 개발자. Java/Spring 중심
- MSA·DDD·CI/CD는 해봤지만, **AI가 들어간 시스템의 운영 문제**는 처음
- 알고 싶은 것: 큐를 어디에 두는가, 멱등성은 어떻게 잡는가, RAG는 어느 계층에 붙는가
- 결과물을 블로그와 발표로 설명할 수 있어야 한다

### 2.2 2차 사용자 — 소규모 팀의 당직 개발자

- 5~20명 규모 개발팀. Slack이 기본 업무 공간
- 장애 알림이 Slack 채널로 온다
- 온콜 중 과거 사례를 빨리 찾고 싶지만, 위키를 뒤질 여유는 없다
- **요구**: 채널을 떠나지 않고, 질문 한 줄로 답을 얻는 것

### 2.3 타겟이 아닌 사람

- 일반 사내 직원 (인사·총무 문의 봇이 아니다)
- 고객 (외부 대응용이 아니다)
- 여러 워크스페이스를 관리하는 운영자 (멀티테넌시는 범위 밖)

## 3. User Flow

### Flow A — 질문하고 답받기 (P0, 핵심)

```
1. 당직자가 #incident 채널에서 봇을 멘션한다
   "@봇 커넥션 풀 고갈 났을 때 예전에 어떻게 처리했었지?"
2. 봇이 즉시 스레드에 "확인 중" 표시를 남긴다        ← P1
3. AI가 답변을 만든다
   (P2: 과거 장애 기록을 검색해 근거로 함께 넣는다)
4. 같은 스레드에 답글이 달린다
   (P2: 참고한 문서 링크를 함께 붙인다)
5. 당직자가 스레드에서 이어서 되묻는다               ← P1
```

**설계 의도**: 답은 반드시 **스레드 안에** 달린다. 채널을 어지럽히지 않고,
질문–답–후속 대화가 한 덩어리로 남아 나중에 그대로 검색 자산이 된다.

### Flow B — 장애 알림이 스스로 리포트가 되기 (P2)

```
1. 모니터링(Grafana/CloudWatch)이 장애를 감지해 Slack에 알림을 쏜다
2. 알림 자체가 트리거가 된다 (사람이 아무것도 하지 않는다)
3. n8n이 알림을 받아 수신 API로 넘긴다
4. AI가 알림 내용 + 과거 유사 장애를 묶어 초안 리포트를 만든다
5. 같은 스레드에 "추정 원인 / 과거 유사 사례 / 1차 대응" 형태로 달린다
```

**이 흐름이 n8n이 필요해지는 지점이다.** 입력이 Slack 하나뿐이면 n8n은 없어도 된다.
입력이 둘 이상이 되는 순간부터 값을 한다.

### Flow C — 실패했을 때 (P0)

```
1. LLM 호출이 실패하거나 P0의 LLM 처리 예산 50초를 초과한다
2. 남은 처리 예산 안에서 "지금은 답할 수 없다"는 안내 전송을 1회 시도한다
3. 안내 전송도 실패하면 event_id·실패 단계·전송 결과를 로그에 남긴다
   (P0: 자동 복구 보장 없음. P1: 재시도·DLQ 정책 적용)
```

**원칙**: 실패 안내를 시도하고, 안내조차 전달하지 못한 실패도 추적 가능하게 남긴다.
Slack 전송 장애 시 사용자 안내의 도달까지 보장하지는 않는다.

## 4. 기능 요구사항

우선순위는 학습 단계와 맞물린다. **P0가 끝나기 전에 P1을 시작하지 않는다.**

### P0 — 1단계 · 이게 없으면 프로젝트가 성립하지 않는다

| ID | 요구사항 | 완료 기준 |
|---|---|---|
| P0-1 | Slack 멘션을 수신한다 | `app_mention` 이벤트를 받아 파싱한다 |
| P0-2 | 요청 서명을 검증한다 | 서명 불일치·5분 초과 요청을 401로 거부한다 |
| P0-3 | 봇 자신의 메시지를 무시한다 | `bot_id`/`subtype` 있는 이벤트를 걸러 무한 루프가 없다 |
| P0-4 | 로컬 LLM으로 답변을 만든다 | Ollama 호출 성공. **API 비용 0원** |
| P0-5 | 원 메시지 스레드에 답글을 단다 | `thread_ts`가 원 메시지를 가리킨다 |
| P0-6 | 실패 안내와 실패 기록을 남긴다 | LLM 실패·시간 초과 시 Slack이 정상이면 안내가 달린다. 안내 전송 실패·결과 불명 시 event_id와 실패 단계가 로그에 남는다 |
| P0-7 | **3초 초과 현상을 재현하고 계측한다** | 재전송 횟수·중복 억제 수·중복 답글 수·LLM 소요 시간이 로그와 `docs/EXPERIMENT-LOG.md`에 남는다. 중복 답글이 0이어도 재전송 관찰로 성립한다 |
| P0-8 | 단일 프로세스에서 중복 처리를 억제한다 | 동일 event_id의 동시 실행을 막고, 답변 또는 실패 안내 전송 성공 후 완료 처리한다. 보장 범위와 실패 처리는 아래 정책을 따른다 |

> P0-7이 이 단계의 진짜 산출물이다. 나머지는 이걸 관찰하기 위한 장치다.

> **완료 판정 규칙**: 정상 흐름은 **실제 외부 왕복 성공**, 거부·실패 흐름은 오류를 유도해 기대한 응답·안내·로그를 확인해야 한다.
> `./gradlew build`나 컨텍스트 기동은 완료가 아니다 — 이전 프로토타입이 그 둘을 통과하고도
> 존재하지 않는 모델을 호출하고 있었다 ([`ARCHITECTURE.md`](ARCHITECTURE.md) §7).

### P1 — 2단계 · 실제로 쓸 수 있게 만든다

| ID | 요구사항 | 완료 기준 |
|---|---|---|
| P1-1 | 수신과 처리를 분리한다 | 큐 저장 성공을 확인한 뒤 200을 반환한다. §5 검증 조건에서 수신 응답 p95가 200ms 이내다 |
| P1-2 | 메시지 큐를 둔다 | 워커가 큐를 소비해 처리한다. 수신 서버 재시작에도 요청이 유실되지 않는다 |
| P1-3 | 재전송·재시작 시 중복 처리를 억제한다 | §5의 중복 검증에서 동일 event_id의 최종 답글은 1개다. 완료 상태를 영속화하고, 전송 결과 불명 건은 별도로 기록·복구한다 |
| P1-4 | 실패를 재시도한다 | 재시도 가능한 일시 실패는 최대 3회 재시도한다. 최종 안내도 실패하면 DLQ, 전송 결과 불명은 별도 복구 대상으로 남긴다 (§5 및 ARCHITECTURE.md §5.1) |
| P1-5 | 즉시 반응을 보여준다 | 멘션 직후 "확인 중" 표시(이모지 또는 임시 메시지)가 달린다 |
| P1-6 | 스레드 문맥을 이어받는다 | 같은 스레드의 이전 대화를 프롬프트에 포함한다 |
| P1-7 | 처리 현황을 관측한다 | 처리 시간·큐 적체·실패율을 로그 또는 지표로 확인할 수 있다 |
| P1-8 | 인스턴스를 늘려도 동작한다 | dedup 상태가 프로세스 밖(Redis 등)에 있다 |

### P2 — 3단계 이후 · AI를 시스템답게 만든다

| ID | 요구사항 | 완료 기준 |
|---|---|---|
| P2-1 | 과거 문서를 색인한다 | 장애 리포트를 임베딩해 저장한다 (로컬 임베딩 모델) |
| P2-2 | 질문과 유사한 문서를 찾는다 | 상위 K건을 검색해 프롬프트에 넣는다 |
| P2-3 | 근거를 함께 보여준다 | 답변에 참고 문서 출처가 붙는다 |
| P2-4 | RAG 전후를 비교한다 | 같은 질문에 대한 답변 차이가 기록으로 남는다 |
| P2-5 | 요청 종류에 따라 흐름을 나눈다 | 장애 질문 / 단순 질문 / 정보 부족을 구분해 다르게 처리한다 |
| P2-6 | 역할별로 모델을 나눈다 | 답변용·검색용 모델을 분리한다 |
| P2-7 | Slack 외 입력을 받는다 | 모니터링 알림이 n8n을 거쳐 같은 API로 들어온다 |
| P2-8 | 알림을 리포트로 바꾼다 | Flow B가 사람 개입 없이 끝까지 돈다 |

## 5. 비기능 요구사항

| 항목 | 요구 | 근거 |
|---|---|---|
| **비용** | LLM 추론 비용 0원 | 사이드 프로젝트. 유료 API를 쓰지 않는다 |
| **응답 지연** | P0: 이벤트 처리 최대 60초(LLM·인위적 지연 최대 50초 + Slack 전송 예산 10초)<br>P1: §5 검증 조건에서 수신 p95 200ms 이내, 답변 p95 30초 이내 | P0의 3초 초과 실험에도 처리 상한은 둔다. P1 답변 시간에는 큐 대기를 포함한다 |
| **처리량** | P1: 서로 다른 event_id 10건 동시 처리 시 유실 0 | P0의 복구·처리량 보장과 구분한다. 동시 100건은 P1 이후 검증 |
| **보안** | 모든 요청 서명 검증. 토큰은 환경변수 | ngrok으로 공개되는 엔드포인트다 |
| **데이터** | 대화 내용이 외부 API로 나가지 않는다 | 로컬 추론의 부수 효과이자 장점 |
| **가용성** | 죽으면 죽은 줄 안다 | 개인 프로젝트. 무중단은 목표가 아니다 |

### 단계별 중복·실패 처리 범위

- **P0**: 단일 프로세스의 인메모리 상태로 처리 중인 동일 `event_id`의 동시 실행을 차단한다. 완료 상태는 10분 유지하며, 그 기간의 재전송은 재처리하지 않는다. 프로세스 재시작 이후에는 보장하지 않는다.
- 답변 또는 실패 안내 중 하나의 전송 성공이 확인되면 완료로 본다. 명확한 전송 실패는 완료로 확정하지 않으며 이후 재전송 시 다시 처리할 수 있다. P0에는 자체 재시도·자동 복구 보장이 없다.
- 전송 요청 후 연결이 끊기는 등 결과를 모르면 `전송 결과 불명`으로 기록하고, P0에서는 10분간 자동 재전송을 억제해 수동 확인 대상으로 남긴다. 이후 재전송·재시작에서 중복 가능성이 있음을 실험 기록에 명시한다.
- **P1**: 상태를 프로세스 밖에 유지하고 큐 재전달·워커 재시작까지 검증한다. 자동 실행 허용 기간은 최초 수신 후 24시간, 완료 상태 보존은 최소 7일이며 미해결 복구 건은 자동 삭제하지 않는다. 외부 전송과 완료 상태 기록 사이의 장애는 단순 dedup만으로 해결된 것으로 간주하지 않는다. 결과 불명 건의 확인·복구 정책을 P1 설계의 필수 항목으로 둔다.
- **P0 시간 제한**: 검증을 통과한 이벤트 처리 시작부터 최대 60초다. 인위적 지연과 LLM 호출은 합계 50초 안에 종료하고 남은 시간은 Slack 전송에 사용한다. 답변 전송 실패 후 추가 안내를 연쇄 시도하지 않으며, 제한 이후 늦게 도착한 LLM 결과로 답글을 보내지 않는다.

### P1 성능·복구 검증 조건

다음은 **목표 기준이며 실측 결과가 아니다.** P1 착수 전에 P0 실측으로 달성 가능성을 확인한다. 목표를 바꾸면 근거와 변경값을 이 문서 및 실험 기록에 남긴 뒤 검증한다.

- **환경 고정**: P0 실측에 사용한 장비의 CPU/GPU·RAM·OS, 실제 Ollama 모델 ID·digest·양자화, Ollama 버전, 출력 토큰 상한과 추론 동시성을 `docs/EXPERIMENT-LOG.md`에 기록하고 P1 비교에서도 유지한다. P1에서 추가되는 워커 수는 검증 전에 정해 모든 배치에 동일하게 적용한다. 값이 미기록이면 성능 검증을 시작하지 않는다.
- **입력 고정**: 같은 질문 세트와 출력 토큰 상한을 사용한다. 워밍업 완료 후 측정하며, 콜드 스타트 결과는 별도로 기록한다.
- **성능 검증**: 서로 다른 event_id 10건을 동시에 보내는 배치를 10회 실행한다(배치 간 처리가 끝난 뒤 다음 배치 시작). 100건 전체에서 수신 p95 ≤ 200ms, 정상 답변 p95 ≤ 30초, 유실·실패·중복 답글 0건이면 합격이다. 실패 안내는 정상 답변으로 세지 않는다.
- **측정 구간**: 수신 시간은 서버 HTTP 요청 진입부터 큐 저장 확인 후 응답 완료까지다. 답변 시간은 최초 서버 수신부터 Slack 발신 성공 응답 확인까지이며, 큐 대기·LLM·발신 시간을 포함한다. 동일 event_id로 단계별 로그를 연결한다.
- **중복 검증**: 하나의 event_id를 동시에 10회 전달하는 경우와 완료 후 다시 전달하는 경우를 분리하고, 각각 최종 답글 1개를 확인한다. 서로 다른 10개 event_id에는 각각 1개씩 총 10개가 달려야 한다.
- **복구 검증**: 큐 저장 이후 수신 서버 재시작, 처리 중 워커 재시작, Slack 전송 직후 완료 기록 전 장애를 각각 유도한다. 수락한 각 이벤트가 답변 완료 또는 추적 가능한 복구 대상·DLQ로 남는지 확인하고, 전송 결과 불명 건은 확인·복구 절차까지 검증한다. 성능 측정과 장애 실험은 분리한다.

### LLM 선택

**Ollama 로컬 추론**을 기본으로 한다.

- 비용 0원, 대화 내용이 밖으로 나가지 않음
- 3단계 임베딩 모델도 같은 Ollama에서 돌릴 수 있어 **멀티 모델 실습이 공짜**
- 느린 것이 단점이 아니라, **3초 제약을 인위적 지연 없이 자연스럽게 재현해 준다**

호출은 **OpenAI 호환 스키마**로만 한다. 벤더를 코드에 박지 않으면
나중에 Groq·Gemini·유료 API로 바꿀 때 `base-url`만 고치면 된다.
